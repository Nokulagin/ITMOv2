# Анализ процесса: AS IS и TO BE

## AS IS

Событие: ревьюер получает diff (TRAINING_PR.diff) и хочет быстрый обзор и риски.

Процесс:
- Ревьюер отправляет diff в REST‑сервис.
- Сервис формирует prompt без явной фильтрации секретов и без строгого ограничения длины.
- Сервис вызывает внешний LLM и ждёт ответ синхронно.
- Ответ возвращается в простой форме (часто «comment»/summary) без гарантированной структуры OUT‑1.

Участники: ревьюер (человек), REST‑сервис, внешний LLM.

Задержки и потери:
- Длинные диффы могут приводить к отказам/таймаутам (REL‑1), нет предсказуемой деградации.
- Нет обязательной редакции секретов (SEC‑1) → риск утечки.
- Zero‑shot ответы нередко без evidence и ссылок на строки (QA‑1 не соблюдается).


## TO BE

Малый инкремент: внедряем Context Pack и master prompt, вводим фильтр секретов и ограничение размера diff, определяем структуру OUT‑1, таймауты переводим в контролируемые ответы.

```mermaid
flowchart LR
    A[Ревьюер отправляет diff] --> B[API валидирует и обрезает до 20k]
    B --> C[Редактор скрывает секреты (SEC-1)]
    C --> D[LLM с master prompt и Context Pack]
    D --> E[Контролируемый ответ OUT-1]
    E --> F[Ревьюер получает summary, ≤3 risks, checks]
```

## Разница

| Что меняется | AS IS | TO BE | Как проверим изменение |
|---|---|---|---|
| Редакция секретов | отсутствует | [REDACTED] для секретов | тест с подставленным токеном |
| Ограничение длины | отсутствует | 20 000 символов, 413 иначе | e2e с длинным входом |
| Формат ответа | произвольный comment | OUT‑1: summary, risks≤3, checks | шаблон валидации |
| Таймауты LLM | 500/немая ошибка | контролируемый ответ | интеграционный тест таймаута |
