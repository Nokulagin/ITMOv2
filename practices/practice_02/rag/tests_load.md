# Нагрузочные проверки

Цели и SLO

- Сбор метрик p50/p95/p99 латентности сервиса и error rate.
- Пределы: p95 ≤ 10 c (сохранено из Практики 1), p99 ≤ 10 c как следствие REL‑1 (таймаут внешнего LLM 10 c; ошибка конвертируется в контролируемый ответ).
- API‑1: 100% HTTP 413 при diff > 20 000 символов; 0% 413 при ≤ 20 000.
- REL‑1: 100% контролируемых таймаутов при внешнем LLM ≥ 10 c; сервис не падает.
- SEC‑1 и OBS‑1: секреты редактируются до [REDACTED]; в логах только request_id, длительность, статус.

Методика

- Прогрев: Требуется решение команды (единое значение для всех прогонов).
- Повторы: ≥3 прогона каждого сценария; фиксировать seed генерации входов.
- Генерация входов: валидные diff; пороговые длины 19 999 / 20 000 / 20 001 символов для API‑1; диффы с тестовыми секретами для SEC‑1.
- Мок внешнего LLM: задержка ≥10 c для проверки REL‑1; контролируемый ответ считается успешным поведением.
- Стабильность стенда: фиксировать версию сервиса и окружение; изолировать внешние зависимости. Требуется решение команды (инструменты нагрузки и формат экспорта).

Приёмка

- Автопроверки порогов:
  - p95 ≤ 10 c; p99 ≤ 10 c.
  - 100% 413 для diff > 20 000; 0% 413 при ≤ 20 000.
  - 100% контролируемых таймаутов при задержке внешнего LLM ≥ 10 c; сервис возвращает контролируемый ответ и не падает.
- Экспорт метрик в CI: p50/p95/p99, error rate, распределение кодов ответов, доля контролируемых таймаутов; формат артефактов — Требуется решение команды.
- Проверка логов: соответствие OBS‑1 (только request_id, длительность, статус; без diff/ответа модели).
- Отчёт: ссылки на артефакты CI, параметры запуска (RPS, длительность, seed), версия стенда.

Политика запуска

- Если нагрузочное тестирование пока не требуется, обосновать и назвать условие, после которого оно понадобится.
- Для учебного сценария полное нагрузочное тестирование опционально. Оно потребуется, если сервис будет использоваться в CI с параллельными ревью (>5 RPS) или при интеграции в_prod среду.
