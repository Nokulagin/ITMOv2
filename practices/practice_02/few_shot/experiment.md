# Few-shot: улучшение tests_load.md (Практика 1 → Практика 2)

- Артефакт Практики 1: `practices/practice_01/tests_load.md`
- Что хотим улучшить: добавить проверяемые SLO (включая p99), расширенные сценарии нагрузки, методику, приёмку и evidence; ввести политику запуска.

## Примеры

### Хороший результат
Строка S3 “Таймаут внешнего LLM (REL‑1)” — есть профиль, пороги p95/p99 и evidence; подтверждена конверсия таймаутов в контролируемые ответы.

### Плохой результат
“Evidence: логи” без проверки секретов и без классификации ошибок.

## Запрос
Few-shot промпт, применённый к исходному файлу Практики 1:

```
Ты — инженер по производительности. Твоя задача: улучшить файл tests_load.md (практика 1) до уровня практики 2. Сохраняй исходную структуру и стиль, усиливай содержимое минимальными корректными изменениями: добавь чёткие SLO, сценарии с профилями нагрузки, критерии приёмки, методику, и evidence. Пиши по-русски.

Контекст и ограничения (используй только это):
- Источники: CASE.md, context.md (Context Pack), сам tests_load.md.
- Соблюдай факты/правила Context Pack:
  - SEC-1: перед внешним LLM секреты редактируются ([REDACTED]); не допускай утечек.
  - API-1: diff > 20 000 символов → HTTP 413.
  - REL-1: таймаут внешнего LLM 10 секунд; ошибка превращается в контролируемый ответ.
  - OUT-1/QA-1: включай только утверждения с evidence; не выдумывай.
  - OBS-1: логируются только request_id, длительность, статус; diff/ответ модели не логируются.
- Не добавляй внешние предположения, противоречащие правилам. Числа и формулировки согласуй с API-1 и REL-1.
- Минимизируй изменения в структуре: не удаляй разделы без необходимости, дополняй и уточняй.

Что нужно получить (ровно один целевой документ — обновлённый tests_load.md):
- Цели и SLO: p95 ≤ 10 с для успешных запросов на заданной нагрузке; p99 (например ≤ 12 с) укажи явно; error rate ≤ 1% при steady-state; 100% 413 для > 20k; для таймаутов — 100% контролируемых ответов.
- Сценарии нагрузки (таблица): сценарий, профиль (ramp-up/steady/ramp-down или burst), RPS, длительность; чёткие пороги приёмки; измерения (латентность p50/p95/p99, коды, распределения, ресурсы для длительных прогонов); evidence/чем сверять (метрики, артефакты CI).
- Методика: разогрев, генерация входных diff (валидные, сверхлимитные, с синтетическими секрет‑паттернами), стабильность стенда, повторяемость (сколько прогонов), инструменты (к6/JMeter/Locust — без навязывания).
- Приёмка: автоматизируемые проверки порогов; отчётность (что приложить).
- Политика запуска: когда нагрузочные тесты не требуются и когда обязательны (CI ≥ 5 RPS; прод; изменения в API‑1/REL‑1/SEC‑1/OBS‑1; рост ошибок/латентности).
- Как использовали AI: коротко, по делу (что согласовали с правилами; как верифицируются SEC‑1/OBS‑1).

Формат результата:
- Верни только полный, улучшённый текст файла tests_load.md. Без пояснений, без преамбулы, без “вот обновлённый файл”. Разделы и таблицы в Markdown.
- Сохрани язык и терминологию артефактов репозитория.

Few-shot примеры (ориентир стиля и глубины изменений) — короткие фрагменты для калибровки:
- A: строка сценария усиливается профилем, порогами p95/p99 и evidence.
- B: опциональность → политика с триггерами (CI ≥ 5 RPS; прод; изменения API‑1/REL‑1/SEC‑1/OBS‑1; деградации).
- C: evidence уточняется под SEC‑1/OBS‑1 (поиск секрет‑паттернов, состав логов).
```
