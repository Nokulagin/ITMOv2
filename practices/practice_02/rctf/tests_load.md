# Нагрузочные проверки

## Цели и SLO
- p95 ≤ 10 с для успешных запросов при целевой нагрузке.
- p99 ≤ 12 с для успешных запросов при целевой нагрузке.
- error rate ≤ 1% в steady‑state (исключая ожидаемые 413 по API‑1).
- Для diff > 20 000 символов — 100% HTTP 413 (API‑1).
- При таймауте внешнего LLM (10 с, REL‑1) — 100% контролируемых ответов; 0 5xx; сервис не падает.

## Методика
- Прогрев: 1 мин перед фиксацией метрик.
- Повторяемость: ≥ 3 прогона ключевых сценариев (S1/S2/S3).
- Генерация входов: валидные diff; пороговые длины 19 999 / 20 000 / 20 001 символов; диффы с безопасными секрет‑паттернами.
- Мок внешнего LLM: режим таймаута 10 с и контроль редактирования секретов ([REDACTED]) без логирования diff/ответов.
- Стабильность стенда: фиксировать версии сервиса/инструментов; изолировать внешние зависимости.
- Инструменты: k6/JMeter/Locust; отчёты и артефакты сохранять в CI.

## Приёмка
- Автопроверки порогов SLO/SLA в CI: латентность p95/p99, error rate, доля 413, контролируемые таймауты.
- Экспорт метрик/графики: p50/p95/p99, распределение кодов, тренды ресурсов/латентности, отчёты сценариев.
- Проверка логов на соответствие OBS‑1: только request_id/длительность/статус; отсутствие содержимого diff/ответа.

## Политика запуска
- Не требуется: локально, < 2 RPS, без CI/параллельных ревью.
- Обязательно: CI ≥ 5 RPS; прод; изменения, затрагивающие API‑1/REL‑1/SEC‑1/OBS‑1; деградации по мониторингу (рост p95/error rate).
