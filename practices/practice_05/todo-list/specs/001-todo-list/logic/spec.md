## Область

В объёме только четыре операции из `AGENTS.md`:

- список задач;
- добавление задачи;
- отметка выполнения и снятие отметки;
- удаление задачи.

Не входит: редактирование названия, фильтры, сортировка, пользователи, несколько списков. Экраны, тексты интерфейса и вёрстка описываются в спецификации UI.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Добавить задачу (Priority: P1)

Клиент присылает название новой задачи. Сервер проверяет название, сохраняет задачу в базе и возвращает созданную задачу с присвоенным `id`.

**Why this priority**: без добавления список не имеет смысла.

**Independent Test**: отправить корректное название и получить 201 с задачей; затем запросить список и увидеть задачу в нём.

**Acceptance Scenarios**:

1. **Given** пустой список, **When** клиент добавляет «Купить молоко», **Then** сервер отвечает 201, в ответе есть `id`, `title = "Купить молоко"`, `done = false`, и задача появляется в списке.
2. **Given** название «  Купить молоко  » с пробелами по краям, **When** клиент добавляет его, **Then** сохраняется «Купить молоко» без пробелов по краям.
3. **Given** название из одного пробела или пустая строка, **When** клиент добавляет его, **Then** сервер отвечает 400 и ничего не сохраняет.

### User Story 2 - Отметить и снять отметку выполнения (Priority: P1)

Клиент помечает задачу выполненной или снимает отметку.

**Why this priority**: это основная цель списка задач.

**Independent Test**: отправить изменение `done` для существующей задачи и проверить, что в списке значение изменилось.

**Acceptance Scenarios**:

1. **Given** задача с `done = false`, **When** клиент отправляет `done = true`, **Then** сервер отвечает 200 и возвращает задачу с `done = true`.
2. **Given** задача с `done = true`, **When** клиент отправляет `done = false`, **Then** сервер отвечает 200 и возвращает задачу с `done = false`.
3. **Given** задача с указанным `id` не существует, **When** клиент отправляет изменение, **Then** сервер отвечает 404 и ничего не меняет.

### User Story 3 - Удалить задачу (Priority: P2)

Клиент удаляет задачу по `id`. Задача исчезает из списка и из базы.

**Why this priority**: нужно для очистки списка, но без него список работает.

**Independent Test**: удалить задачу и проверить, что её нет в списке; повторное удаление даёт 404.

**Acceptance Scenarios**:

1. **Given** задача существует, **When** клиент удаляет её, **Then** сервер отвечает 204 без тела и задача не попадает в список.
2. **Given** задачи с таким `id` нет, **When** клиент удаляет её, **Then** сервер отвечает 404.

### User Story 4 - Получить список (Priority: P1)

Клиент запрашивает все задачи и получает их от новых к старым (по убыванию `id`).

**Why this priority**: нужен для первой загрузки страницы и после каждой операции.

**Independent Test**: добавить три задачи и получить список из трёх элементов в обратном порядке добавления.

**Acceptance Scenarios**:

1. **Given** база пуста, **When** клиент запрашивает список, **Then** сервер отвечает 200 и пустым массивом `[]`.
2. **Given** в базе три задачи, добавленные в порядке A, B, C, **When** клиент запрашивает список, **Then** сервер возвращает C, B, A.

### Edge Cases

- Название ровно 200 символов принимается; 201 символ отклоняется с 400.
- Название из 200 символов с многобайтными буквами (например, кириллица) считается по символам, а не по байтам.
- `id` в пути не число (например, `/api/todos/abc`) — ответ 404, как для неизвестного `id`.
- Тело запроса не JSON или `done` не `true`/`false` — ответ 400.
- Тело запроса больше лимита — ответ 413, база не меняется.
- Повторная отметка (`done = true` для уже выполненной задачи) — ответ 200, без ошибки.
- Файл `data/todos.db` и папка `data/` отсутствуют при старте — создаются автоматически.
- `POST` или `PATCH` без заголовка `Content-Length` (в том числе с `Transfer-Encoding: chunked`) — ответ 411, база не меняется.
- `Content-Length` не число или отрицательный — ответ 400, база не меняется.
- `GET /static/../secret` или файл, которого нет в `static/`, — ответ 404 «Маршрут не найден.».

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Сервер MUST хранить задачи в SQLite-файле `data/todos.db` относительно корня проекта.
- **FR-002**: Сервер MUST создавать папку `data/` и схему таблицы при старте, если их нет. Повторный старт не должен терять данные.
- **FR-003**: Сервер MUST принимать название задачи длиной от 1 до 200 кодовых точек Unicode после обрезки пробелов по краям.
- **FR-004**: Сервер MUST отклонять название, которое пусто или состоит только из пробелов, с кодом 400.
- **FR-005**: Сервер MUST присваивать каждой задаче уникальный целочисленный `id`, который не переиспользуется после удаления (через `AUTOINCREMENT`).
- **FR-006**: Сервер MUST создавать новую задачу с `done = false`.
- **FR-007**: Сервер MUST менять `done` только в значения `true` или `false` по запросу.
- **FR-008**: Сервер MUST возвращать список задач от новых к старым (по убыванию `id`).
- **FR-009**: Сервер MUST возвращать 404 для любой операции с `id`, которого нет в базе.
- **FR-010**: Сервер MUST удалять задачу из базы полностью (не помечать как удалённую).
- **FR-011**: Сервер MUST отклонять тело запроса больше лимита из раздела «Лимиты» кодом 413.
- **FR-012**: Сервер MUST использовать параметризованные SQL-запросы; название задачи не подставляется в текст запроса строкой.
- **FR-013**: Сервер MUST возвращать все ошибки в одном формате с текстом на русском (см. раздел «Ошибки»).
- **FR-014**: Сервер MUST отдавать страницу `GET /` и файлы `GET /static/{имя}` из папки `static/` (контракт, раздел 10).
- **FR-015**: Сервер MUST отклонять запрос с телом без заголовка `Content-Length` (в том числе с `Transfer-Encoding: chunked`) кодом 411, а некорректный `Content-Length` кодом 400 (решение 9).

### Key Entities

- **Задача (todo)**: `id` (целое число, назначает сервер), `title` (текст 1–200 символов), `done` (логическое значение, по умолчанию `false`).
- **Список**: одна упорядоченная коллекция задач. Отдельной сущности «список» нет.

## Данные

| Поле    | Тип в SQLite       | Ограничения                                                   |
|---------|--------------------|----------------------------------------------------------------|
| `id`    | INTEGER            | PRIMARY KEY AUTOINCREMENT; `NOT NULL`                          |
| `title` | TEXT               | `NOT NULL`; после обрезки 1–200 кодовых точек (проверка в коде) |
| `done`  | INTEGER            | `NOT NULL`, `DEFAULT 0`; значения 0 (нет) или 1 (да)           |

В JSON-ответах `done` передаётся как логическое значение `true`/`false`; преобразование делает слой логики.

## Хранилище

- Путь к файлу: `data/todos.db` от корня проекта. Переопределяется флагом `--db` при запуске (решение 8).
- При старте: создать папку `data/`, если её нет; выполнить `CREATE TABLE IF NOT EXISTS` для таблицы задач.
- Соединение с базой открывается и закрывается в рамках каждой операции (решение, см. «Решения», пункт 3).
- Все записи (добавление, изменение, удаление) выполняются в транзакции; при ошибке изменений нет.
- Для тестов путь к базе задаётся отдельно, чтобы не трогать рабочий `data/todos.db`.

## Эндпоинты

Все эндпоинты работают с JSON (`Content-Type: application/json`) и отвечают JSON, кроме `204`.

| Операция | Метод и путь | Тело запроса | Успех | Ошибки |
|---|---|---|---|---|
| Список | `GET /api/todos` | нет | 200, массив задач от новых к старым | 500 |
| Добавить | `POST /api/todos` | `{"title": "строка"}` | 201, задача | 400, 411, 413, 500 |
| Отметить / снять отметку | `PATCH /api/todos/{id}` | `{"done": true}` или `{"done": false}` | 200, задача целиком | 400, 404, 411, 413, 500 |
| Удалить | `DELETE /api/todos/{id}` | нет | 204, без тела | 404, 500 |

Формат задачи в ответе: `{"id": 1, "title": "Купить молоко", "done": false}`.

Формат ошибки: `{"error": "текст ошибки на русском"}`.

Примечание: форма отметки через `PATCH` принята, см. «Решения», пункт 1.

Статика: `GET /` и `GET /static/{имя}` не JSON, а файлы страницы. Описаны в контракте, раздел 10.

## Правила

- **Обрезка пробелов**: до проверки длины убираются пробелы и переводы строк по краям названия. Внутренние пробелы не меняются.
- **Длина**: считается в кодовых точках Unicode, после обрезки. Так же считает UI (контракт, раздел 6).
- **Тип `title`**: должно быть строкой. Число, `null`, массив — 400.
- **Тип `done`**: только логическое значение `true` или `false`. Строка `"true"`, число `1` — 400.
- **Лишние поля** в теле запроса игнорируются.
- **Порядок списка**: по убыванию `id`, то есть новые задачи сверху (решение человека). Сортировки по запросу нет.
- **Неизвестный `id`**: любой `id`, которого нет в базе, включая нечисловой, даёт 404. Изменение базы не происходит.
- **Идентификаторы не переиспользуются**: после удаления новая задача получает новый `id` (через `AUTOINCREMENT`).
- **Повторная отметка** одного и того же значения не считается ошибкой.
- **Content-Length**: запрос с телом (`POST`, `PATCH`) без заголовка `Content-Length`, в том числе с `Transfer-Encoding: chunked`, отклоняется кодом 411. Некорректный заголовок (не число или отрицательный) — кодом 400 (решение 9).
- **Один клиент, один список**: авторизации и разделения данных нет.
- **Однопоточность**: сервер обрабатывает один запрос за раз (`http.server.HTTPServer`), параллельных записей в базу нет. Тесты на одновременные запросы не нужны.

## Алгоритмы

### Список (`GET /api/todos`)

1. Выбрать все строки таблицы, отсортированные по `id` по убыванию.
2. Преобразовать каждую строку: `done` из 0/1 в `false`/`true`.
3. Вернуть 200 с массивом (пустой массив, если задач нет).

### Добавление (`POST /api/todos`)

1. Проверить заголовок `Content-Length`: нет — 411, некорректный — 400. Если тело больше лимита, вернуть 413 и выйти.
2. Разобрать тело как JSON. Если не получилось или это не объект — 400.
3. Взять `title`. Если его нет или не строка — 400.
4. Обрезать пробелы по краям.
5. Если длина 0 или больше 200 кодовых точек — 400.
6. В транзакции вставить строку с `title` и `done = 0`; получить назначенный `id`.
7. Вернуть 201 с задачей (`done = false`).

### Отметка / снятие (`PATCH /api/todos/{id}`)

1. Проверить заголовок `Content-Length`: нет — 411, некорректный — 400. Если тело больше лимита — 413.
2. Разобрать тело как JSON-объект. Если не получилось — 400.
3. Взять `done`. Если его нет или это не `true`/`false` — 400.
4. Разобрать `id` из пути. Если он не целое положительное число — 404.
5. В транзакции найти задачу по `id`. Если её нет — 404.
6. Обновить `done` значением 1 или 0.
7. Прочитать задачу заново и вернуть 200.

Порядок проверок (контракт, раздел 3): заголовок и размер (400, 411, 413), затем тело (400), затем `done` (400), затем `id` (404). Так неверное тело на несуществующей задаче даёт 400, а не 404, а нечисловой `id` тоже даёт 404, но только после проверки тела.

### Удаление (`DELETE /api/todos/{id}`)

1. Разобрать `id` из пути. Если он не целое положительное число — 404.
2. В транзакции удалить строку с этим `id`.
3. Если строк не удалено — 404.
4. Вернуть 204 без тела.

### Статика (`GET /`, `GET /static/{имя}`)

1. Путь `/` — отдать `static/index.html` с `200` и `text/html; charset=utf-8`.
2. Путь `/static/{имя}` — имя не должно содержать `/` и `..`. Если файл есть в `static/`, отдать его с `200` и типом по расширению (`.css`, `.js`).
3. Иначе — `404` «Маршрут не найден.».

## Ошибки

| Код | Когда | Текст `error` |
|---|---|---|
| 400 | `Content-Length` не число или отрицательный | `Некорректный заголовок Content-Length.` |
| 400 | тело не JSON или не объект | `Тело запроса должно быть JSON-объектом.` |
| 400 | `title` отсутствует или не строка | `Название задачи должно быть строкой.` |
| 400 | `title` пустое после обрезки | `Название задачи не может быть пустым.` |
| 400 | `title` длиннее 200 символов | `Название задачи не должно быть длиннее 200 символов.` |
| 400 | `done` отсутствует или не логическое значение | `Поле done должно быть true или false.` |
| 404 | `id` не найден или не число | `Задача не найдена.` |
| 404 | неизвестный путь | `Маршрут не найден.` |
| 405 | метод не поддерживается для пути | `Метод не поддерживается.` |
| 411 | тело без `Content-Length` (в том числе chunked) | `Требуется заголовок Content-Length.` |
| 413 | тело больше лимита | `Тело запроса слишком большое.` |
| 500 | ошибка базы данных | `Внутренняя ошибка сервера.` |

Ошибка 500 не раскрывает детали (путь к файлу, текст исключения) клиенту; детали пишутся в журнал сервера.

## Лимиты

- Максимальный размер тела запроса: **4 КБ** (4096 байт). См. «Решения», пункт 4.
- Название: 200 кодовых точек Unicode после обрезки.
- Лимит тела проверяется до разбора JSON.

## Проверки (тест-кейсы для unittest)

Тесты пишутся на `unittest` и используют временную базу. Команда запуска: `python3 -m unittest discover -s server/tests -t . -v` (решение 11).

**Хранилище и старт**

1. Старт с отсутствующей папкой `data/` создаёт её и таблицу.
2. Повторный старт не удаляет существующие задачи.

**Добавление**

3. Корректное название создаёт задачу с `done = false` и `id`.
4. Название с пробелами по краям сохраняется обрезанным.
5. Название из 1 символа принимается.
6. Название из 200 символов принимается.
7. Название из 201 символа отклоняется с 400.
8. Название из 200 кириллических букв принимается; 201 отклоняется.
9. Пустая строка и строка из пробелов отклоняются с 400.
10. Число вместо строки в `title` даёт 400.
11. Тело не JSON даёт 400.
12. Тело больше 4 КБ даёт 413, база не меняется.

**Отметка и снятие**

13. `done = true` для существующей задачи возвращает 200 и `done = true`.
14. `done = false` снимает отметку.
15. Повторная отметка того же значения даёт 200.
16. `done = "true"` (строка) даёт 400.
17. Отсутствие поля `done` даёт 400.
18. Отметка несуществующего `id` даёт 404, база не меняется.
19. Нечисловой `id` в пути (`abc`) даёт 404.

**Удаление**

20. Удаление существующей задачи возвращает 204, задачи нет в списке.
21. Повторное удаление того же `id` даёт 404.
22. Удаление несуществующего `id` даёт 404.
23. После удаления новая задача получает `id` больше удалённого (без переиспользования).

**Список**

24. Пустая база даёт `[]`.
25. Три задачи возвращаются от новых к старым.
26. Список после отметки показывает новое значение `done`.

**Устойчивость**

27. Параметризованные запросы: название с кавычками и `;` сохраняется как есть, таблица не ломается.

**Статика и заголовки** (`server/tests/test_api.py`)

28. `GET /` отдаёт `static/index.html` с `200` и `text/html`.
29. `GET /static/styles.css` и `GET /static/app.js` отдают файлы с `200` и правильным типом.
30. Неизвестный файл статики и путь с `..` дают `404`.
31. `POST` с телом без `Content-Length` даёт `411`, база не меняется.

## Что не входит в изменение

- Редактирование названия задачи.
- Фильтры (выполненные / невыполненные), поиск, сортировка по запросу.
- Пользователи, авторизация, несколько списков.
- Экраны, тексты интерфейса, вёрстка, JavaScript на странице.
- Пагинация списка.
- Поля `created_at`, `updated_at` и подобные: в `AGENTS.md` их нет.
- Миграции схемы: первая версия таблицы создаётся при старте.

## Решения

Ответ человека 2026-10-20: принято по рекомендациям логического агента. Ниже каждое решение с пометкой «Решение».

1. **Форма эндпоинтов для отметки.** Варианты: (A) `PATCH /api/todos/{id}` с телом `{"done": bool}`; (B) два пути `POST /api/todos/{id}/done` и `POST /api/todos/{id}/undone`. **Решение: A**, одна операция с одним телом, меньше путей и проще тесты.
2. **Удаление: тело ответа.** Варианты: (A) `204` без тела; (B) `200` с удалённой задачей. **Решение: A**, стандартно для удаления и не нужно UI.
3. **Соединения с базой.** Варианты: (A) открывать соединение на каждую операцию; (B) одно соединение на процесс с блокировкой. **Решение: A**, проще и безопаснее для стандартного `http.server`, нагрузка учебная.
4. **Лимит тела 4 КБ.** Альтернатива: 1 КБ. В UTF-8 200 эмодзи занимают 800 байт, но при JSON-экранировании (`😀`, `А`) 200 эмодзи занимают до 2400 байт, а 200 кириллических букв — до 1200 байт, плюс служебные поля. **Решение: 4 КБ**, с запасом.
5. **Поле `created_at`.** В `AGENTS.md` не указано. **Решение: не добавлять**, чтобы не расширять объём без решения человека.
6. **Порядок проверок: сначала тело, потом существование.** Выбран порядок: тело (400), затем `id` в базе (404). **Решение: оставить как описано**, чтобы неверный запрос всегда давал 400.
7. **Библиотеки.** Используются только `http.server` и `sqlite3`, как в `AGENTS.md` и конституции. Перед написанием кода API этих модулей проверяется через context7; если context7 недоступен, это сообщается человеку, без угадывания API.
8. **Путь к базе и порт (C7).** Варианты: (A) только параметр конструктора, без флагов; (B) флаги `--db` и `--port` при запуске. **Решение: B**: флаги `--db` (по умолчанию `data/todos.db` от корня проекта) и `--port` (по умолчанию 8000). Тесты используют параметр конструктора и временную базу, а не флаг.
9. **Content-Length (C6).** Варианты: (A) считать тело пустым при отсутствии заголовка; (B) отвечать 411. **Решение: B**, 411 для запроса с телом без заголовка, 400 для некорректного значения.
10. **Раздача страницы (C1).** Варианты: (A) сервер логики отдаёт `static/`; (B) отдельный сервер для страницы. **Решение: A**, один origin для страницы и API (контракт, раздел 10).
11. **Команда тестов (C5).** **Решение:** `python3 -m unittest discover -s server/tests -t . -v`. Записана здесь и в контракте, раздел 10. В планах и quickstart используется эта команда.
12. **Файл `data/todos.db` и `.gitignore` (C7).** **Решение:** `data/` в git не попадает. Запись `data/` добавляется в `.gitignore` при реализации, без отдельного согласования: решение уже принято.
