**Prerequisites**: plan.md (обязательно), spec.md (обязательно). Контракт применяется в задачах через ссылки на его разделы.

**Tests**: автоматических UI-тестов нет. В спецификации и плане их не просили; конституция (принцип V) требует ручной проверки по `quickstart.md`. Тестовых задач здесь нет, проверка вынесена в финальную фазу.

**Organization**: задачи сгруппированы по пользовательским историям из `spec.md`: US4 (загрузка, P1), US1 (добавление, P1), US2 (отметка, P2), US3 (удаление, P3).

## Открытые решения, которые блокируют отдельные задачи

- **Длина названия (решено)**: кодовые точки Unicode после обрезки, контракт 1.1 (раздел 6, сводка решений, п. 2). Не блокирует задачи. Проверка длины на клиенте выполняется в T014.
- **Тексты интерфейса**: помечены «предложено». Задачи T005, T006, T010, T016, T021, T025 используют их как есть; при изменении текстов правятся эти задачи и `spec.md`.
- **Размещение файлов** закрыто контрактом 1.1 (раздел 10): страница в `todo-list/static/`, раздаёт её логика. Пути в задачах обновлены.
- **Приоритеты** по контракту 1.1 и `spec.md`: US1, US2, US4 — P1; US3 — P2. Совпадают, расхождения нет (`plan.md`, «Открытые решения», п. 4 закрыт).

## Format: `[ID] [P?] [Story] Description`

- **[P]**: можно выполнять параллельно (разные файлы, нет зависимостей от незавершённых задач).
- **[Story]**: US1, US2, US3, US4; только в фазах пользовательских историй.

## Path Conventions

## Dependencies & Execution Order

### Phase Dependencies

- **Setup (Phase 1)**: без зависимостей; T001, T002, T003 можно делать параллельно
- **Foundational (Phase 2)**: после Setup; блокирует все истории
- **US4 (Phase 3)**: после Phase 2; нужна для любых проверок, потому что список загружается при открытии
- **US1 (Phase 4)**: после US4 (отрисовка и перезагрузка списка)
- **US2 (Phase 5)**: после US4 (нужен список с `id`)
- **US3 (Phase 6)**: после US4
- **Polish (Phase 7)**: после всех историй

### User Story Dependencies

- Все истории зависят от загрузки списка (US4), поэтому порядок такой: US4 → US1 → US2 → US3. Пункт спецификации о параллельной работе неприменим, потому что все истории меняют один файл `app.js`.
- Задачи внутри одного файла (`app.js`) выполняются последовательно: параллельных `[P]` там нет.

### Parallel Opportunities

- Phase 1: T001, T002, T003 (разные файлы).
- Phase 2: T008 (`styles.css`) можно вести параллельно с T004–T007 (`app.js`); T009 идёт после T008, потому что оба в `styles.css`.
- Phase 7: T025 можно делать параллельно с T026 и T027, если разные файлы.

## Implementation Strategy

### MVP First (User Stories 4 и 1)

1. Phase 1: Setup
2. Phase 2: Foundational
3. Phase 3: US4 (загрузка)
4. Phase 4: US1 (добавление), после решения по длине названия (T014)
5. **STOP и проверка**: открыть страницу, добавить задачу, перезагрузить — задача на месте

### Incremental Delivery

1. Setup + Foundational → каркас
2. US4 → список при открытии
3. US1 → добавление (MVP)
4. US2 → отметка
5. US3 → удаление
6. Polish → клавиатура, адаптивность, контраст, ручная проверка

## Notes

- Пункты `[P]` стоят только там, где задачи трогают разные файлы.
- Тексты интерфейса берутся из `spec.md`, коды ошибок и поведение — из `contract.md`. Не расширять API и не придумывать новые тексты.
- Если решение по длине названия или текстам изменится, правятся T014, T025 и соответствующие задачи, а не контракт без согласия человека.
