## Summary

Одна страница со списком задач: форма добавления (название 1–200 символов), отметка выполнения, удаление, счётчик «Выполнено: N из M». Данные берутся из `GET /api/todos`, изменения отправляются через `POST`, `PATCH` и `DELETE` (контракт, раздел 3). После каждой успешной операции UI заново запрашивает список (контракт, раздел 5 и правило 8 в сводке решений). Список показывается в порядке от логики: новые задачи сверху.

Технический подход: статическая страница из HTML, CSS и JavaScript без фреймворков и сборки (`AGENTS.md`, конституция). Всё поведение на клиенте: загрузить список, отправить изменение, запросить список заново и перерисовать, показать текст состояния по коду ответа.

## Technical Context

**Language/Version**: HTML5, CSS3, JavaScript (ES2017+, без транспиляции). Браузер: современный, с поддержкой `fetch`.

**Primary Dependencies**: нет. Без фреймворков, библиотек, CDN и npm (`AGENTS.md`, конституция). Документация библиотек не нужна: используются только встроенные возможности браузера.

**Storage**: нет на стороне UI. Данные хранятся логикой (SQLite `data/todos.db`); UI ничего не сохраняет в `localStorage`.

**Testing**: ручной чек-лист по `quickstart.md` и `spec.md` (клавиатура, адаптивность 360/768/1280 px, контраст, тексты, состояния). Автоматического UI-теста нет (конституция, принцип V).

**Target Platform**: современный браузер; страница и API на одном origin, пути `/api/todos` (контракт, раздел 1).

**Project Type**: web (статическая страница, одна).

**Performance Goals**: цифр нет ни в спецификации, ни в контракте. Не вводим, пока человек не задаст.

**Constraints**: без горизонтальной прокрутки при 360, 768 и 1280 px; контраст не ниже WCAG AA; все тексты на русском; видимый фокус; работа с клавиатуры; тело запроса не больше 4096 байт (контракт, раздел 1).

**Scale/Scope**: один список, одна страница, четыре операции: загрузка, добавить, отметить, удалить.

## Phase 1: Design

### Эндпоинты, которые использует UI (по контракту)

| Действие UI | Запрос | Успех | Что делает UI дальше |
|---|---|---|---|
| Загрузка при открытии | `GET /api/todos` | `200`, массив | Отрисовать список; при пустом массиве показать пустое состояние |
| Добавление | `POST /api/todos`, тело `{"title": ...}` | `201`, задача | Очистить поле, фокус в поле, заново запросить список |
| Отметка | `PATCH /api/todos/{id}`, тело `{"done": true}` или `{"done": false}` | `200`, задача | Заново запросить список |
| Удаление | `DELETE /api/todos/{id}` | `204` | Заново запросить список |

Ошибки и тексты состояний — по таблице раздела 5 контракта. Тексты самого UI берутся из `spec.md`, раздел «Тексты интерфейса»; текст `error` из ответа сервера UI не показывает (контракт, раздел 1).

### Правила клиента, которые следуют из контракта

- **Длина названия**: UI обрезает пробелы и переводы строк по краям, затем считает кодовые точки (контракт, раздел 6). Проверка на клиенте не отправляет запрос, если название пустое или длиннее 200 кодовых точек.
- **Атрибут `maxlength`** на поле не ставим (контракт, раздел 5): иначе сообщение о 201 символе не появится.
- **Кнопка «Добавить»** блокируется на время запроса добавления (решено: Q2, ответ A).
- **Порядок списка** не сортируем: список отображается как пришёл из `GET` (новые сверху).
- **Счётчик** пересчитывается из загруженного списка; скрыт при пустом списке (контракт, сводка решений, строка 12).
- **Тело запроса** отправляется только с `Content-Type: application/json` (контракт, раздел 1). Браузер сам ставит `Content-Length` для строкового тела `fetch`, поэтому код `411` (раздел 4) на клиенте не возникает, но UI его обрабатывает так же, как `413` и `500` (раздел 5).
- **Фокус после отметки** остаётся на флажке той же задачи (контракт, решение 20).
- **Фокус после удаления** по правилу из `spec.md`, раздел «Клавиатура».
