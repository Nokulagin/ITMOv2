# Todo-list Constitution

Учебный проект ДЗ5: одна страница, список задач в SQLite, две спецификации (UI и логика),
общий контракт, затем код. Этот документ задаёт правила, которые не меняются от задачи к задаче.
Список задач и текущий статус живут в `AGENTS.md`.

## Core Principles

### I. Контракт — единственная общая правда

Спецификации `specs/001-todo-list/ui/spec.md` и `specs/001-todo-list/logic/spec.md` пишутся
независимо. Расхождения между ними снимаются только через `specs/001-todo-list/contract.md`.

- `contract.md` создаётся только после того, как обе спецификации готовы.
- Код не пишется до того, как человек утвердил контракт.
- Изменить `contract.md` может только человек или агент с его прямого согласия.

Rationale: два агента в разных сессиях иначе разойдутся в эндпоинтах, текстах ошибок и формате
данных, и проблема всплывёт только при интеграции.

### II. Каждый агент правит только свой файл

- UI-агент правит только `ui/spec.md`, логический агент только `logic/spec.md`.
- Вопросы к другой стороне записываются в раздел «Вопросы к контракту» своего файла.
- Ни один агент не правит чужой файл, `AGENTS.md`, эту конституцию или шаблоны Spec Kit.

Rationale: файлы не пересекаются, поэтому сессии могут работать параллельно без конфликтов.

### III. Решения принимает человек

- Агент предлагает варианты с рекомендацией и не утверждает решение сам.
- Переход к следующему этапу (обсуждение → спецификации → контракт → код) выполняется только
  после явного разрешения человека.
- Если задача или требование неясны, агент задаёт вопрос, а не угадывает.

Rationale: ворота этапов — учебная цель проекта, и проверять их должен человек.

### IV. Документация только через context7

- Документацию библиотек, фреймворков и стандартной библиотеки Python агенты берут через
  MCP-сервер `context7` (`.mcp.json`), а не из памяти модели.
- Если context7 недоступен, агент сообщает об этом человеку и не придумывает API.

Rationale: память модели может устареть или ошибаться в деталях API, а проверка через context7
дешевле исправления ошибки в коде.

### V. Проверяемость

- Логика покрывается тестами `unittest` из стандартной библиотеки.
- UI проверяется ручным чек-листом по `ui-spec.md` (клавиатура, адаптивность, контраст, ошибки).
- Строгий TDD (тесты первыми, Red-Green-Refactor) не обязателен.
- Работа считается готовой, когда выполнены пункты `AGENTS.md`, проверки зелёные и субагент
  сверки не находит расхождений между спецификациями, контрактом и кодом.

Rationale: учебный проект должен показывать, что требования реально проверены, а не только
записаны.

## Технические ограничения

- **Бэкенд:** Python 3, только стандартная библиотека (`http.server`, `sqlite3`). Пакеты через
  pip не устанавливаются.
- **Фронтенд:** HTML, CSS и JavaScript без фреймворков, библиотек, CDN и шагов сборки.
- **Хранилище:** SQLite-файл `data/todos.db`.
- **Язык:** спецификации, контракт и тексты для человека на русском. Код, имена и комментарии
  в коде на английском.
- **Спецификации:** только GitHub Spec Kit. Другие SDD-фреймворки, включая OpenSpec, не используем.
- **Объём:** только операции из `AGENTS.md` (добавить, отметить и снять отметку, удалить).
  Всё остальное из раздела «Не входит в проект» вне объёма, пока человек не решит иначе.
- **Качество интерфейса:** работа с клавиатуры, видимый фокус, адаптивность при 360, 768 и 1280 px
  без горизонтальной прокрутки, контраст текста не ниже WCAG AA.

## Рабочий процесс

- Все работают в одной ветке `2026_Nokulagin_practice_5`. Ветки под спецификации не создаём.
- Порядок этапов: обсуждение задач → конституция → спецификации UI и логики → обсуждение и
  контракт → план и задачи Spec Kit → реализация → проверка субагентами.
- Для спецификаций используются команды Spec Kit: `/speckit-specify`, `/speckit-clarify`.
  Для проверки используются `/speckit-analyze` и `/speckit-checklist`.
- Проверка на шаге реализации: два read-only субагента (спецификации ↔ код, `AGENTS.md` ↔ код)
  и `/speckit-analyze`. Субагенты не правят код.

## Governance

- Эта конституция имеет приоритет над остальными практиками проекта, включая `AGENTS.md`.
  При противоречии действует конституция, а `AGENTS.md` исправляется.
- Изменения вносит человек. Агент может предложить изменение, но применяет его только после
  явного согласия.
- Версия меняется по semver:
  - MAJOR: принцип удалён или его смысл изменён несовместимо;
  - MINOR: добавлен новый принцип или раздел, либо существенно расширено правило;
  - PATCH: формулировки, опечатки и уточнения без смены смысла.
- Перед каждым этапом агент проверяет соответствие конституции и сообщает человеку, если что-то
  не соответствует.
- Новые технические ограничения, например внешняя библиотека, требуют изменения этого документа
  (MINOR или MAJOR), а не решения «по ходу».
