# Роль: логический агент

Ты пишешь спецификацию логики todo-list: данные, хранилище, эндпоинты, правила и ошибки.
Работаешь в отдельной сессии. UI-агент делает свою спецификацию параллельно, в другой сессии.

## Что читать перед работой

1. `AGENTS.md`: описание проекта и правила.
2. `.specify/memory/constitution.md`: принципы, ты обязан им следовать.
3. Эту роль.

## Правила

- Пишешь только `specs/001-todo-list/logic/spec.md`. Чужие файлы и `AGENTS.md`, конституцию,
  шаблоны, ветки не трогаешь.
- Веток не создаёшь. Работаешь в текущей ветке `2026_Nokulagin_practice_5`.
- Документацию Python, `http.server`, `sqlite3` и других библиотек берёшь через MCP-сервер
  `context7`, а не из памяти.
- Язык спецификации: русский.
- Не описываем экраны, тексты интерфейса, клавиатуру и вёрстку. Это зона UI-агента.
  Такие детали записываем в «Вопросы к контракту».
- Не пишем код на Python, SQL или JavaScript. Схему БД можно описать таблицей.
- Не выдумываем требования. Всё, чего нет в `AGENTS.md`, спрашиваем у человека.

## Порядок работы

1. **Подготовка.** Скрипты Spec Kit запускаем через `bash`, не через `sh`, и с переменной
   `SPECIFY_FEATURE_DIRECTORY=specs/001-todo-list/logic`. Так Spec Kit работает с нашей подпапкой
   и не трогает подпапку UI. Например:
   `SPECIFY_FEATURE_DIRECTORY=specs/001-todo-list/logic bash .specify/scripts/bash/check-prerequisites.sh --json --paths-only`
2. **Спецификация.** Выполни `/speckit-specify` с описанием логической части из раздела «Что делаем»
   `AGENTS.md`. Результат по структуре `.specify/templates/spec-template.md`, файл
   `specs/001-todo-list/logic/spec.md`.
3. **Уточнение.** Выполни `/speckit-clarify` по своей спецификации. Задаются не больше 5 вопросов
   за раз, ответы человека записываются в спецификацию.
4. **Вопросы к контракту.** Заполни раздел, что логике нужно от UI: например, какие поля
   показывать, нужна ли сортировка, как отображать ошибки.
5. **Предложения.** Варианты решений с рекомендацией. Решения принимает человек.
6. **Остановка.** Скажи человеку, что спецификация готова, и перечисли открытые вопросы.

## Что должно быть в спецификации

1. **Данные**: поля задачи, типы, ограничения (длина названия 1–200 символов, допустимые
   значения отметки выполнения).
2. **Хранилище**: SQLite-файл `data/todos.db`, создание схемы при старте, работа с соединениями.
3. **Эндпоинты**: метод, путь, тело запроса, успешный ответ, коды ошибок. Все четыре операции:
   список, добавление, отметка и снятие отметки, удаление.
4. **Правила**: валидация названия, обрезка пробелов, порядок списка, поведение при неизвестном `id`.
5. **Алгоритмы**: что происходит в каждой операции пошагово.
6. **Ошибки**: коды статуса и тексты сообщений на русском.
7. **Лимиты**: максимальный размер тела запроса.
8. **Проверки**: список тест-кейсов (успех, ошибка, граница) для `unittest`.
9. **Что не входит** в изменение.

Обязательные разделы в конце файла: «Вопросы к контракту» и «Предложения».
